# 011 — Database access, roles, migrations and the first schema

- **Status:** Accepted (amended by [ADR 014](014-containers-and-local-compose.md) and by P7, see Amendments)
- **Date:** 2026-09-20

## Context

P3 needed a real PostgreSQL + pgvector database, a safe way to change its schema, and a boundary so
that the running application cannot reshape the database it uses. ADR 001 already chose one PostgreSQL
database and said the pgvector extension is enabled by the first migration, not by Terraform (RDS is in
private subnets, so Terraform cannot run SQL there). This ADR records how that is done.

## Decision

### 1. Two database roles

| Role | Used by | Can |
|---|---|---|
| **Migration role** (locally the Compose admin user; on AWS the RDS master user) | Alembic only | Create the extension, create, alter and drop tables |
| **Runtime role** `stock_app` | The `api` and `worker` | Connect, `SELECT`/`INSERT`/`UPDATE`/`DELETE` on tables. **No DDL**: it cannot create, alter, drop or truncate, and cannot create extensions |

- A running container never holds DDL rights, so a bug or an injection in the application cannot drop
  or reshape tables.
- `ALTER DEFAULT PRIVILEGES` (set once by the local init script) gives the runtime role DML on every
  table the migration role creates, and nothing more.
- Locally the init script `docker/postgres-init/01-roles-and-databases.sh` creates the runtime role,
  the second database used by tests, and the grants. **On AWS** the same bootstrap is a one-off ECS task
  of its own (Terraform cannot run SQL against an instance in isolated subnets); see the amendment of
  2026-09-22 below.

### 2. Alembic, written by hand

- Migrations are versioned Python scripts with `upgrade()` and `downgrade()`. Alembic records the
  current revision in the `alembic_version` table. Every environment reaches the same schema by running
  the same ordered steps. Schema changes happen **only** through migrations, one migration per phase.
- **Forward-only in production.** `downgrade()` exists so local development and tests can prove a
  migration is reversible (`up, down, up`).
- Hand-written, not autogenerated: there are no ORM models yet, and a small explicit script is easier
  to explain and review. *(Amended 2026-09-21: this sentence originally said ORM models would arrive
  with the follow API in P5. They did not: [ADR 013](013-follow-api-and-frontend-shell.md) keeps plain
  SQL, so migrations stay hand-written and there is still nothing to autogenerate from.)*
- PostgreSQL supports transactional DDL, so each upgrade or downgrade is all-or-nothing.
- The async `env.py` connects with asyncpg through a `NullPool` engine (one short job needs one
  connection). Offline SQL mode is deliberately unsupported.

### 3. The migration URL is separate from application configuration

- `MIGRATION_DATABASE_URL` is read **only** by `migrations/env.py`: from the process environment first,
  then from a separate git-ignored `.env.migration` file (local convenience). It is **not** a field of the
  application's `Settings`, so the API and worker cannot read it, and it is never printed. A missing URL
  raises a clear error that names the variable and no value.
- `alembic.ini` holds no URL and no credentials (a test enforces this).
- On AWS the variable exists only in the one-off migration ECS task, never in the `api` or `worker`
  containers.

### 4. The first migration (`0001`)

- `CREATE EXTENSION IF NOT EXISTS vector`: needs a privileged role, so it lives in the migration and is
  reversed by `downgrade`. **No vector column exists yet**; the `vector(1024)` embedding column arrives
  with `chunks` in P10 (ADR 010 fixed the dimension).
- Table `stocks`: `id` identity bigint, `symbol` (unique, checked against the same
  `^[A-Z0-9&-]{1,20}$` pattern the API uses), `name`, `bse_code` (text, unique, exactly six digits),
  `sector`, `is_financial`, `created_at timestamptz`. Constraints have explicit names (`pk_stocks`,
  `uq_stocks_symbol`, `uq_stocks_bse_code`, `ck_stocks_symbol_format`, `ck_stocks_bse_code_format`).
  No ISIN column: the MVP does not need it, and adding one later is a single migration.
- **Seed:** exactly RELIANCE, TCS and HDFCBANK, written into the migration file as deterministic values
  and inserted with parameterised `INSERT ... ON CONFLICT (symbol) DO NOTHING`. A fresh database is
  reproduced by the migration alone: no data file, no network. Adding a stock is a new migration.

| Symbol | BSE code | Name | Sector (NSE "Industry") | `is_financial` |
|---|---|---|---|---|
| RELIANCE | 500325 | Reliance Industries Limited | Oil Gas & Consumable Fuels | false |
| TCS | 532540 | Tata Consultancy Services Limited | Information Technology | false |
| HDFCBANK | 500180 | HDFC Bank Limited | Financial Services | true |

**Where the values come from.** BSE codes for RELIANCE and HDFCBANK come from each company's own filing
to BSE and NSE; TCS's was confirmed by the owner on BSE's own stock page (BSE, `tcs.com` and NSE's
archive block automated access, so they were not scraped). Sector values are the `Industry` column of
NSE's published Nifty 50 constituent list (`ind_nifty50list.csv`), used verbatim; that file was used
**only to verify the values** and is kept out of git in `data/local/`. Names are the full legal names as
listed on NSE (the CSV abbreviates them to "Ltd."). `is_financial` is **our** classification (ADR 009:
debt-to-equity is "not applicable" for banks), not an exchange fact.

### 5. Testing

Integration tests run against the Docker Compose database and Alembic, with no Testcontainers. Every
integration session first rebuilds the test database from the migrations alone (downgrade to base, then
upgrade to head), so no test trusts leftover state. Tests prove: up, down, up with the database
verified after each step; no half-applied state; the runtime role cannot run migrations; the URL rules
(environment beats file, missing URL is an error); the exact seed values, column types and constraint
names; the seed statement is idempotent; the cosine operator and a 1024-dimension vector work; and no
vector columns exist yet.

## Alternatives considered

| Option | Why not |
|---|---|
| Terraform creates the schema or extension | Terraform cannot reach RDS in private subnets; it also mixes infrastructure with application data |
| Plain SQL scripts run by hand | No record of what ran, no ordering, no rollback for tests |
| Alembic autogenerate from models | There are no models yet; hand-written is smaller and easier to explain |
| One database role for everything | A bug or injection could drop or alter tables |
| Migration URL in the application `.env` / `Settings` | Would put the privileged credential inside the API's reach |
| Read the seed from the CSV at migration time | Makes the migration depend on a local file; the seed must be self-contained and reproducible |
| Testcontainers | Extra dependency; the Compose database is enough (owner's decision) |

## Tradeoffs and known limits

- **Superuser locally, `rds_superuser` on AWS.** The Compose admin user is a real superuser. RDS's master
  user is not. Both can create the extension and tables; check the difference (and the RDS pgvector
  version, which may not equal the pinned local `0.8.6`) in P7.
- **Default privileges also cover `alembic_version`,** so the runtime role could edit the revision row.
  Doing so would need an already-compromised application; a separate schema for it is not worth the
  complexity here.
- **The runtime role can write to `stocks`** (reference data changed only by migrations). The important
  boundary is "no DDL"; tightening reference tables to read-only is possible later.
- **Init scripts run only when the data volume is first created.** Changing roles or grants means
  `docker compose down -v` locally.

## Consequences for other decisions

- ADR 001 is fulfilled: the extension is enabled by the first migration.
- ADR 008: the deploy pipeline runs `alembic upgrade head` in a one-off ECS task with migration
  credentials; the long-running service holds only runtime credentials.
- P4 onward adds one migration per phase for that phase's tables.
- ADR 013 (P5) decided that data access stays plain SQL (`text()`), not an ORM, as it was in P4.

## Amendments

### 2026-09-21: the two roles in containers (P6, [ADR 014](014-containers-and-local-compose.md))

The decision above is unchanged; P6 makes it true of running containers, and tests it.

- The Compose service `migrate` is the local counterpart of the one-off ECS migration task. It runs
  `alembic upgrade head` from the backend image and is the **only** service given
  `MIGRATION_DATABASE_URL` and the admin credentials. The `api` container receives the runtime role's
  `DATABASE_URL` and nothing that can change the schema. Tests fail if `api` or `web` is given the admin
  credentials, if a container is given an `env_file`, or if the migrate command is missing its URL.
- Inside containers the migration URL comes only from the environment. The git-ignored `.env.migration`
  is a host-side convenience and is never used in a container.
- The application's `DATABASE_URL` used by the containers is derived by Compose (runtime role, host `db`).
  The `DATABASE_URL` in `.env` is for tools run on the host.
- The limits above are unchanged: the local admin role is a superuser and RDS's is not, and the roles'
  bootstrap script still runs only when the data volume is first created.

### 2026-09-22: who creates the runtime role on AWS (P7)

Section 1 left the mechanism open. Building the AWS stack made the gap concrete: **nothing was creating
`stock_app` on RDS**, so the two-role boundary would not have existed there at all. RDS creates the
database and the master user and stops; it has no `docker-entrypoint-initdb.d`. The api container would
still have started (the engine opens no connection until the first query, so `/api/healthz` passes), and
the first real query — `/api/readyz`, or signing in — would have failed.

Terraform cannot close the gap: the instance is in the isolated subnets with no public access, so a
`postgresql` provider running on a laptop or in CI cannot reach it. The fix has to run **inside the VPC**.

**Decision: a third one-off ECS task, `provision`, running `python -m app.db.provision` from the same
backend image** (`infra/stack/compute.tf`, `backend/src/app/db/provision.py`).

- **Not inside an Alembic migration.** Alembic versions the *schema*. Putting role creation and a
  password there would put credential management into schema history, and make every environment's
  migration depend on a runtime secret being present. `CREATE EXTENSION` is in migration `0001` because
  an extension is part of the schema; a login role is not.
- **A separate task, not a step inside `migrate`.** Each is separately re-runnable and separately
  readable in its own log group, and `migrate` keeps the exact argv `alembic upgrade head`.
- **It reads the runtime password out of the runtime URL.** That password is generated ephemerally and
  stored write-only in SSM, so after the apply nobody — including Terraform — can read it back. The task
  is therefore given both parameters: the admin URL to connect with, the runtime URL to read the role and
  password from. No new IAM: the migration execution role already grants exactly those two parameters.
- **Idempotent and order-independent.** An existing role is `ALTER`ed rather than `CREATE`d, so a rotated
  password takes effect; the grants are applied both `ON ALL TABLES` (for what the migration has already
  created) and through `ALTER DEFAULT PRIVILEGES` (for what it creates later), so `provision` and
  `migrate` may run in either order and either may be re-run.
- **The SQL is the same SQL as the local init script**, which is the point: one boundary, one
  explanation, proven in `backend/tests/integration/test_provision_db.py` against a database that never
  ran the script.

Role name and password are interpolated into DDL, because PostgreSQL does not accept bound parameters
there. Both are validated against a strict allow-list first and refused rather than escaped; the password
is alphanumeric by construction (`special = false` in `infra/stack/secrets.tf`).
